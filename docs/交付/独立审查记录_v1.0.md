### S1-01 Agent 知识查询读的是文件知识库，而正式导入不生成它

**问题**：`locate_knowledge`、`get_knowledge_detail`、`get_knowledge_relations`、`list_knowledge_candidates` 的注册入口从 `KnowledgeStore(data_root)` 读取文件快照；正式导入只写数据库 `versions`，没有调用 `ingest_textbook_snapshot` 或 `publish_verified`。干净部署导入后，学生问“知识点定位”会得到 `KB_NOT_FOUND` 或 `KB_NOT_PUBLISHED`，而不是正式知识版本。

**证据**：

- `src/study_companion/agent/knowledge_tools.py:55`：`store = KnowledgeStore(data_root)`；`:56-60`：按文件快照校验目录与 `kb.status`。
- `src/study_companion/recommendation/query.py:447-452`：材料按 `kp_ids` 筛选时同样读 `KnowledgeStore` 的 `current.json`。
- `src/study_companion/pipeline.py:1334-1365`：正式导入调用 `build_knowledge` 后只 `repo.create_version`，没有写文件知识库。
- 全仓检索 `publish_verified` 只有 `knowledge/store.py` 定义和测试调用，没有生产调用方；`ingest_textbook` 同样只有定义。
- `tests/agent/test_knowledge_tools.py:26-31`、`tests/api/test_chat_knowledge.py:29`：测试自己 `save_draft` 造文件快照，所以测试通过，但正式链路不会生成这份快照。

**影响**：在干净环境（REL-01 场景）里，知识查询、材料按知识点筛选、前置关系查询这三类能力不可用。即便机器上残留旧文件快照，它也有自己的 `current.json` 指针，可能和数据库正式 `knowledge` 版本不一致，违反 02 §9“不得另写第二个 current 指针作为真值”。

**建议修复**：二选一，且只保留一条真值：让 A 的正式导入把已发布知识版本写入 `KnowledgeStore`（带 `publish_verified` 和版本绑定），或让 Agent 工具直接读数据库 `versions(kind=knowledge)` 与正式指针。材料 `kp_ids` 筛选也改读同一来源。必须补一条“干净库导入后知识查询可用”的集成测试。

**是否需要改代码**：是。

### S1-02 C 的模型复核被预算截断，规则审核又能单独把方案标为 validated

**问题**：正式方案审核先跑 `review_plan_rules`，再尝试一次模型复核；模型复核每个任务最多 4 份方案，微课堂模型生成每个任务最多 6 份。预算耗尽、未配置模型或模型失败时，代码保留规则审核结果，而规则审核的六项检查并没有真正核对证据、材料存在性、重复与泄答，仍可能给出 `validated` 并发布。

**证据**：

- `src/study_companion/pipeline.py:114-130`：`PLAN_REVIEW_LIMIT = int(os.getenv("C_PLAN_REVIEW_LIMIT", "4"))`，每个 job 只允许 4 次模型复核。
- `src/study_companion/pipeline.py:145-148`：模型调用异常、未配置或预算用尽时直接返回 `rule_review`。
- `src/study_companion/pipeline.py:1507`、`:2267`：发布条件就是 `review.status == "validated"`，没有区分“规则 validated”和“完整审核 validated”。
- `src/study_companion/recommendation/planner.py:1263-1312`：六项规则检查里 `material_history` 恒为 `True`，`answer_guard` 只检查每个活动是否有 0 或 3 条提示，`evidence` 只检查引用列表非空，未核对引用是否真实支撑结论。
- `src/study_companion/pipeline.py:878-889`：`LESSON_MODEL_LIMIT` 默认 6，每个 job 最多 6 节微课堂走模型，其余直接规则模板。
- `_local/acceptance-20261128-004728/summary.json:70-79`：真实全量回归 154 份微课堂全部 `creation_method=rule`、`review_status=validated`；`summary.json:59-68`：78 个已发布方案头全部 `validated`，只有 D14 两方案被模型复核拦下。也就是说，其余 76 个方案没有模型复核记录。

**影响**：C 的“完整审核”只在少数方案上真实发生，绝大多数方案靠规则门自动发布。D14 被拦下恰好证明模型复核有效，但也反证其余方案没有被同样审核。微课堂在真实回归中没有留下任何模型生成产物，交付材料不能据此声称“微课堂模型生成、独立复核”已经形成真实证据。

**建议修复**：按方案/微课堂逐份执行完整审核，预算按 04 §5.3 的“每次方案最多 8 次”记账，不设全局 4/6 的截断；如果必须截断，规则结果不能标 `validated`，只能 `needs_review`，并把这个限制写进方案、导出和验收证据。规则审核的 `material_history` 与 `answer_guard` 必须落到真实材料与受保护题干。

**是否需要改代码**：是。

## 5. S3 级

### S3-01 模型预算字典只增不清

**影响**：长时间运行或重试场景下，模型预算会比预期更早耗尽；内存增长很小，但行为不可预测。
