# 湛知｜智慧学伴设计方案

| 项目 | 内容 |
|---|---|
| 参赛赛题 | 智慧学伴：理解学科、理解学生、理解教学 |
| 作品名称 | 湛知（本地双端智慧学伴） |
| 系统形态 | 单机部署的教师端 + 学生端 Web 应用 |
| 文档版本 | v2.0（2026-11-28），配套成果包 777,652 字节 |

全文八章。第 1 章讲需求，第 2 章讲方案，第 3 章讲打开界面能看到什么，第 4 章讲证据，第 5 至 8 章讲创新、平台、依据和限制。每节开头先用一两句话说明这一节回答什么问题，正文里的数字都能在成果包或仓库记录里找到对应出处。

## 摘要

湛知把赛方给的课程要求、题库和模拟作答，加工成三层可核对的成果：结构化课程知识、有证据的学情诊断、可执行也能调整的学习方案。做法上有一条主线：数字全部由规则算出，模型只负责理解和表达，模型产物再交给另一次独立调用复核。2026-11-28 的干净库回归用赛方六张 CSV 加一份教材切片跑通全链路，得到 40 名学生、2 个班、37 个知识点、11 条关系、80 份学情、80 份方案、159 个任务组和 160 份微课堂，全程 22 分 03 秒。第一次导出被质量门拦下，修的是生成逻辑，重跑之后才出包；最终成果包 777,652 字节，799 条证据的引用全部可解析。

> 配套交付物：这份设计方案、正式成果包（16 个文件、777,652 字节）、答辩 PPT 与五分钟演示视频。时间紧的评委可以先翻第 4 章看数字，再回到第 2 章看这些数字是怎么产生的。

## 1 需求分析

这一章回答三件事：赛题到底要什么，师生实际会怎么用它，为什么方案最后长成现在这样。三件事按顺序看完，后面章节的设计取舍就不难理解。

### 1.1 三道题，一条链

赛题给的是七年级数学的课程要求、65 份题目与材料、2 个测验节点，以及 40 名模拟学生的作答记录。三道题一层比一层具体：这门课要教什么，这些学生学到哪儿了，下一步该怎么教。

湛知把三道题做成一条链。A 模块读课程要求与教材，整理出知识点、关系和题目标注；B 模块读 A 的正式版本和有效作答，算出个人与班级的学情；C 模块读 A、B 的正式版本，排出任务组、活动和微课堂；教师端、学生端、Agent 和导出读的是同一套正式结果，谁都不另存一份。

| 赛题要求 | 系统交出什么 | 评委怎么核 |
|---|---|---|
| 理解学科 | 37 个知识点、11 条关系、58 条题目与评分点标注，每条都带出处 | 课程体系页点开任一知识点；包内 `knowledge_graph.json` 与 `materials_index.json` |
| 理解学生 | 40 名学生、2 个班、2 个节点的 80 份学情，指标带分子分母，诊断带原题与作答 | 班级总览看分布与共性，学生画像展开诊断；包内 `student_analysis.json` |
| 理解教学 | 80 份方案、159 个任务组、160 份微课堂，按证据选策略、定顺序 | 学生端直接按任务组学习；包内 `recommendations.json` 与 `micro_lessons.json` |

边界也写在前面。系统不做注册与账号体系，不做分布式云部署，不做模型训练，也不把模拟学情包装成真实教学成效。赛题的模拟数据只能证明系统给出的结果、证据和建议是合理的，不能证明教学效果本身。

### 1.2 教师和学生各自的一天

这一节换个角度看需求：不问系统有什么功能，只问教师早上打开电脑会做什么，学生晚上打开手机会做什么。

教师通常从班级总览开始。选一个班、一个节点，先看雷达图和共性薄弱项，再看掌握分布和重点关注名单；名册里的分母包含没有作答记录的学生，不会把他们悄悄剔掉。想追一名学生时，从名册点进画像，看到某条诊断觉得可疑，就在原地展开它引用的原题、作答和评分点，抽屉里还能继续往下翻。发现课程体系里有 23 条候选点待处理，就逐条通过、拒绝或改一改，系统不会因为点了“通过”就跳过证据检查。想调一次计划，直接在对话里说“把 D01 下一组练习减到 3 题”，系统先给候选差异，教师确认后才发布。

学生那边只有三件事。打开个人画像，看到自己的指标、一段文字诊断和最近的进展，页面明确区分“优势”“需要加强”“暂需更多证据”，没有足够证据的知识点不会被打成薄弱。进学习计划，按任务组顺序做微课堂、学习卡和题目，没满足前置的活动是锁着的。卡住时逐级要提示，第一层给知识点线索，第二层给方法方向，第三层才点出尚未完成的关键动作。提交之后，选择题和填空题当场出分，解答题先显示“已提交，待评分”，等模型初评和独立复核都走完再给分。

这两种视角最后汇到同一条要求上：页面上每个数字都要能点开看依据，看不到依据的数字不该出现在页面上。

### 1.3 为什么规则和模型都要

这一节解释一个绕不开的选择：模型既然能写字，要不要让它把数字也一起算了。

只靠规则会退化成关键词匹配。知识点合并、题目与评分点的语义对齐、学生解题步骤的错因、教学语言的组织，这几件事没法用有限规则穷举；硬写规则也能跑，但会产出看起来精确、实际错误的结论。只靠模型则失去可复现性：同一份作答两次评分可能不一样，指标的分子分母对不上，审核没有稳定基准，评委也没法逐条核对。

湛知把两件事切开，并规定交界处的数据形态。规则负责一切进入结论的计算与判定，模型负责语义理解与表达，交界处只允许结构化草稿通过。

| 环节 | 谁定值 | 谁释义 |
|---|---|---|
| 数据清洗、指标统计、掌握状态 | 规则 | 不参与 |
| 知识提取与关系判断 | 结构校验、环检测、引用检查 | 知识点、关系、题目对齐 |
| 选择题与填空题评分 | 规则判分与等价表达 | 不参与 |
| 解答题评分 | 分数范围、分项合计、作答依据校验 | 按评分细则分点评分 |
| 策略、选题、负担与顺序 | 六类策略、候选资格、优先级 | 在合法候选内组合并写教学语言 |
| 审核 | 身份、版本、材料、结构、数学、答案保护 | 依据是否成立、顺序是否合理 |

交界处有三条硬约束：模型只输出结构化草稿，程序再做结构、引用、范围和答案保护校验；模型不能改数字、不能写正式状态、不能直接发布；模型失败必须显式记录，降级结果要标出真实生成方式。这套分工在真实数据上被反向验证过一次，D14 两个节点的方案被复核判为不通过，系统没有放行，导出因此被阻断，详见 4.3。

## 2 方案设计

这一章回答系统怎么搭、数据怎么流动，以及为什么这么搭能经得起追问。先给全貌，再走一遍主链路和回流链路，最后说明版本与证据是怎么绑在一起的。

### 2.1 一张图看全貌

这一节先给一张全貌图：系统分成哪几层，每层负责什么。

整体是模块化单体：一个 Python/FastAPI 后端、一个 SQLite 数据库、一套 React/TypeScript 前端，单机启动。A、B、C 的业务逻辑写成纯函数，服务层负责装配上下文和持久化；Agent 只能经受控工具读写业务服务；Web 只做展示与提交。好处很实际：评委核对一类结论，只读一个模块就够。

```text
教师端 / 学生端（React + TypeScript，只做展示与提交）
      │  HTTP /api/v1：统一包络、会话鉴权、幂等键、按角色裁剪          ▼
FastAPI 路由层（鉴权、参数校验、错误映射、任务回执）
      ├─ A 课程知识      ├─ B 学情与评分      ├─ C 策略与方案
      ├─ Agent：受控工具循环，写操作只生成候选
      ├─ 模型服务：统一适配、结构化输出、失败上报
      └─ 调度：outbox → job → step，单机 worker，租约与恢复            ▼
SQLite：唯一正式状态（版本、正式指针、发布记录、依赖边、证据索引、事件账本）
      └─ 导出：冻结快照 → 依赖闭包 → 组装 ZIP → 回读校验
```

模块之间的禁止项同样写在设计里。A 不推断学生掌握程度，也不生成题目和难度值；B 不自建推荐策略，不改写课程知识；C 不创造未登记题目，不改写 B 的结论；Agent 不绕过 C 的审核和权限，也不直接写库；导出只打包冻结的正式成果，不趁机重算另一份业务结果。

### 2.2 一次导入到成果

这一节走一遍主链路：教师传六个 CSV，最后拿到一份可下载的成果包，中间发生了什么。

教师上传后先确认文件分类，系统建立数据快照与目录，然后按依赖顺序跑四步。顺序由依赖决定，教师不用手点：知识正式发布后，才按可用范围投递个人与班级分析；分析正式之后才有方案任务。任何一步失败只影响下游，已发布且仍适用的旧版本继续可读，页面标为待更新。

| 步骤 | 做什么 | 40 人数据实测 |
|---|---|---|
| load | 读原始行，建快照与目录 | 0.62 秒 |
| knowledge | 范围计划、分块提取、去重、关系、题目对齐、独立复核、发布 | 12 分 59.94 秒 |
| analysis | 清洗、指标、掌握状态、错因诊断、班级汇总 | 1 分 41.88 秒 |
| plans | 需求聚合、策略、选题、任务组、微课堂、审核、发布 | 7 分 21.05 秒 |

耗时结构说明成本花在哪：纯数据装配几乎不花时间，知识构建占了大头，因为要读教材页面、调模型提取并做关系判断；方案生成次之，因为每份方案都要过审核。四步合计 22 分 03.69 秒。

状态被拆成三个互不替代的维度：执行状态（等待、运行、成功、失败、取消）、审核状态（草稿、待复核、通过、拒绝）、发布状态（未发布、已发布、被取代）。四步“成功”只说明任务跑完了，不说明内容通过审核，更不说明学生能看到。页面上的“已发布”必须对应一条真实发布记录和一个可读的正式指针，三者缺一个就只能显示未完成。

### 2.3 一次作答的回流

这一节讲静态成果之外的另一半：学生真的开始做题以后，系统怎么更新，更新的范围有多大。

学生开始活动，服务端建尝试、写开始事件，返回题目的安全视图；提交答案时先落库并置为待评分，再调评分；评分完成后写一条评分修订事件，不可靠的评分被隔离，不给有效分；一个任务组做完，服务端按必需活动判定组完成，写事件并入队；随后只重算这名学生受影响的知识点，班级汇总刷新对应成员版本；C 读新学情判断原方案是否还适用，适用就只写一条检查记录，不造新版本。

三个细节决定了这条闭环的可信度。事件账本只追加、不修改，帮助事件和作答事件记在同一个账本里，B 判断“这次是不是独立完成”时读账本，不读前端声明。评分失败时保存提交并置为待评分，不会把空分当零分。方案复查没有实质变化时保持原版本，只在适用性记录里追加一行，避免学生每做一道题就冒出一串没有差异的新方案。

### 2.4 版本和证据怎么串起来

这一节回答评委最常追问的一类问题：这份结论当时依据什么，后来数据变了它还算不算数。

系统里七类标识各管一段：输入快照、题库目录、知识版本、个人分析版本、班级分析版本、方案版本、微课堂正文版本。每份成果都记着自己用的上游版本和事件截点，读到它就能顺着往上追。依赖写进库里，是一组带角色的有向无环边：回归库里知识依赖 391 条、学情依赖 311 条、正文依赖 160 条、目录依赖 85 条、班级对成员 80 条、方案对父版本 77 条。

发布用条件更新切换正式指针：版本号、代次和所需代次三者同时匹配才写入，零行即回滚并返回冲突。两个任务同时想发布同一名学生的新方案时，晚到的那个不会盖掉先到的正式结果。历史版本不删除，读取时按精确版本解析。

| 评委会问 | 系统怎么回答 | 在哪能核 |
|---|---|---|
| 这份建议当时依据哪次学情 | 方案里记着分析版本、知识版本和事件截点 | 方案版本信息、包内版本清单 |
| 学情后来又变了，旧方案还算数吗 | 单独一条适用性记录，结论是适用、部分适用或不适用 | 方案详情、包内 `basis_warnings` |
| 两个任务同时发布会不会互相覆盖 | 发布走条件更新，版本或代次对不上就回滚报冲突 | 发布记录与冲突返回 |
| 页面的数、Agent 说的数、包里的数为什么一致 | 三处都读同一个正式指针，不各自重算 | 同一版本号与同一份证据 |

## 3 功能说明

这一章回答打开系统之后看到什么。教师四个页面、学生三个页面，外加一个对话入口和一份导出包，每个入口只说一件事：它替用户回答什么问题。

### 3.1 教师端

先看教师端最常走的四个入口，以及统一提醒和证据抽屉这两个公共能力。

四个页面按教师的真实动线排，不按系统模块排。

| 页面 | 回答什么问题 | 打开后看到什么 |
|---|---|---|
| 班级总览 | 这个班整体怎么样，谁需要关注 | 班级与节点切换、雷达、共性薄弱项、掌握分布、名册、班级对比 |
| 学生画像 | 这名学生卡在哪，依据是什么 | 概览、进展、作答记录、方案四个页签，诊断可展开到证据抽屉 |
| 课程体系 | 知识图谱长什么样，哪些候选待处理 | 主题分页、关系图、图例、候选审核、质量报告 |
| 数据管理 | 这批数据质量如何，成果能不能导出 | 上传与分类确认、任务链进度、质量报告、导出预检与下载 |

两个公共能力值得单独说。统一提醒入口把 A 的候选异常、C 的方案审核、B 的教师介入汇成三类待办，点进去直达具体对象；已读不等于已处理，结案要填原因并带上证据截点。证据抽屉按引用类型分五种渲染：作答记录、指标、课程与知识、派生结论、学习事件；每种都显示精确版本、适用范围和可继续展开的关联引用，不会把一整段 JSON 原样推给教师看。

方案有三条发布路径，教师需要知道自己走的是哪条。自动生成走完整审核后自动发布；Agent 发起的修改走同一套审核，只多一条真实授权记录；教师在编辑器里直接改，只需通过身份、版本、数据、材料、历史和答案保护这些硬检查，教学合理性警告可以知悉后继续，发布标记为人工确认。三条路径都留版本、原因、历史和恢复记录。

### 3.2 学生端

学生的路径更短。先看三个页面分别解决什么问题，再看作答和提示的细节。

学生端只有三个页面：个人画像、学习计划、AI 对话。

个人画像只读本人的正式结果，展示指标、文字诊断、学习进展和本人依据，明确区分“优势”“需要加强”“暂需更多证据”。学习计划按任务组组织，每组有目标、主策略、预计时长、预期结果和必需活动；活动状态由服务端根据真实事件维护，前端只算“已完成必需活动数 / 总数”，不自己判定组完成。作答支持选择、填空、解答三种题型，解答题保留原始换行和数学符号，中文输入法组词期间不会误触发提交。

三级提示按层释放，每请求一层，服务端记一条真实事件，重读同一层不重复计数。独立补证或迁移检查的题目多一道门：先明确告知“获取帮助后本题不再作为独立完成的证据”，学生选择继续才释放内容，这个选择本身也记进账本。

提交后的反馈分两级。逐题反馈显示得分、评分点和安全提示；整组反馈要等 B 完成局部重分析、C 完成复查之后才出现，而且只显示真实发生的变化。待评分和待复核期间，页面写“已提交，待评分”，不显示 0 分。

### 3.3 Agent 对话

对话入口能做什么、不能做什么，一次修改又是怎么走完的，这一节说清楚。

Agent 是对话入口。它承担八类任务，权限按角色切开，所有事实都从业务工具查。

| 能做什么 | 教师 | 学生 |
|---|---|---|
| 学情查询与解释 | 授权班级 | 本人 |
| 班级学情分析 | 授权班级 | 禁止 |
| 课程知识与关系查询 | 允许 | 授权资料 |
| 方案查询与解释 | 允许 | 本人 |
| 方案修改 | 明确授权范围 | 禁止 |
| 知识讲解与解题引导 | 允许 | 允许，受答案保护 |
| 数据质量查询 | 允许 | 禁止 |
| 学习进展分析 | 允许 | 本人 |

能力边界写进了执行循环：任务路由最多六个子任务、依赖无环；工具白名单按任务与角色下发，参数由程序校验目标、版本和范围；模型提出的写请求只生成候选，提交由服务端按授权记录触发；每次工具调用留轨迹，前端显示中文阶段和状态，不显示参数、内部推理或密钥。

举个完整的例子。教师说“把 D01 下一组练习减到 3 题”，系统先读该生当前正式方案（假设是 V7），C 在规则基线上给出 5 题减到 3 题的候选，Agent 核对候选差异是否落在教师明确授权的范围里；教师确认后提交，任务走完整审核并发布为 V8，回复里给出真实的版本差异。确认时如果该生方案已被另一次操作改成 V9，提交返回 409，原候选不执行，系统提示重新预览，不会把旧候选硬套到新版本上。

含糊请求的处理方式相反。教师说“帮他调整一下”，系统不直接执行，先按授权范围列出对象和拟改内容，等教师在确认卡上选；批量请求先固定名单，逐人准备候选、逐人审核、逐人提交，其中一人失败不影响其他人，失败的学生保留原方案并单独列出。

### 3.4 微课堂

微课堂是什么，正文为什么由封闭组件拼起来，这一节给出答案。

微课堂是学习计划里的独立活动，不算题目、不占题库编号、不产生分数。它解决的是“这个知识点我讲不清、题又不够”的场景。

正文由六类封闭组件组成，服务端定 schema，前端按类型渲染。组件少而封闭，是为了让数学检查做得动。

| 组件 | 做什么 | 检查什么 |
|---|---|---|
| text | 段落讲解 | 纯文本转义，不解析 HTML |
| formula | 单个公式 | 受限表达式解析后排版，非法退回修复 |
| derivation | 分步推导 | 相邻步骤按系数或解集比较，拒绝增根、丢根、翻号 |
| contrast | 正误对照 | 正确式与原始式等价，错误式确实不等价 |
| number_line | 数轴与区间 | 有理数精确比较端点与开闭，交集独立验算 |
| citation | 引用 | 索引存在且已授权，学生看不到教师专有证据 |

生成走 fail-closed。模型产出先过结构与长度校验，再过八项内容复核：数学、每步推导、证据、出处、结构、后续题答案、步骤相似、顺序与诊断污染。任一项不过，先做一次最小修复；仍不过就退回已审核的规则模板，绝不把没验证过的内容发给学生。本轮 160 份微课堂里，154 份由规则模板生成，6 份由真实模型生成并通过八项复核，引用组件 160 条全部能解析到知识点和知识版本。

### 3.5 成果导出

导出回答的是“把什么交给评委”。做法是先冻结一份选择，再按选择组装，不做整库搬运。

冻结时锁定每个对象的精确版本、事件截点、政策哈希和范围，然后做依赖闭包：方案要带上它生成时用的学情版本，班级要带上全部名册成员的个人版本，微课堂要带上正文版本。任何一环缺失或未发布，导出直接拒绝，不做降级拼装。

| 包内文件 | 装了什么 | 对应哪道题 |
|---|---|---|
| `curriculum.json`、`knowledge_graph.json`、`materials_index.json` | 课程要求、知识点与关系、题目与教材索引及出处 | 理解学科 |
| `student_analysis.json`、`class_analysis.json`、`data_quality.json` | 逐生指标与诊断、班级分布与共性、原始行处置 | 理解学生 |
| `recommendations.json`、`micro_lessons.json` | 任务组、活动、理由与顺序；微课堂正文与证据 | 理解教学 |
| `learning_history.json`、`learning_progress.json`、`metrics.csv` | 作答与帮助事件、进展比较、与 JSON 同源的指标表 | 调整依据与核对 |
| `manifest.json`、`README.md`、`field_dictionary.json`、`examples/` | 版本清单、逐文件哈希、字段说明、三案例输入输出 | 可核对性 |

包内 JSON 与 CSV 必须同值。manifest 记版本清单、依赖边、覆盖范围、逐文件哈希和两段校验状态；ZIP 先在暂存区构建，回读校验 CRC、哈希、字节数、记录数和引用可解析性，全部通过才落位并把状态置为就绪。下载只读已就绪的冻结文件，重复下载不重算。

这一节讲本轮最有说服力的一次验证：一次失败被质量门拦住，然后从根上修好。

第一次导出时，方案复核判了 D14 的两个节点不通过。N01 的方案得分率 0.91，文字却说“存在具体错误”，证据和策略对不上；N02 的活动标题与受保护题干一模一样，部分活动还缺独立检查。全库预检因此 `ready=false`，阻塞项写的是 `PLAN_UNPUBLISHED / D14`，导出返回 422 `EXPORT_INCOMPLETE`，没有生成半包。同一轮还发现 D17 的 N02 方案 0 组 0 推荐却已按旧规则发布。

| 对象 | 问题与处置 |

| D14 / N01 方案 | 高分却写成存在具体错误，证据与策略不一致，判待复核，不发布 |

## 5 创新点

这一章讲五个我们自己认为值得说的做法。每一条都在 4.6 那份包里留下了痕迹，评委可以顺着痕迹反查。

### 5.1 规则定值，模型释义，再加一次独立复核

这一节讲系统最核心的一条分工。

所有进入结论的数字由规则算出，模型只负责把结论讲清楚，并且不许改动数字、诊断依据和引用。B 的指标、掌握状态、评分校验如此；C 的策略判定、候选资格、优先级和负担控制也如此，模型只在合法候选集合内调整组合和表达。好处很直接：同一份输入任何时候重放都得到同一组数字，把模型关掉再跑一遍，结论依然成立，4.5 那轮干跑就是这么跑的。

真正把这条分工撑住的是独立复核。每个模型产物都另起一次调用做复核，复核方只拿待审对象和原始依据，不拿生成方的理由或自评。去重需要两次独立判断都判“同一”才合并；关系、映射、方案和微课堂各有检查清单，缺项、重复、伪造依据一律判失败。代价是模型调用量大约翻倍，一轮方案生成要跑优化、内容、独立审核、修复、复审五类任务，每份方案八次请求封顶，超出就暂停并保留上一份可靠方案。我们认为这笔账划算：错误内容一旦发到学生端就撤不回来，多一次复核只是多花几十秒。

### 5.2 版本依赖与证据闭包

“可追溯”在湛知里是一条机制，这一节讲它怎么落地。

多数系统说可追溯，靠的是日志和命名约定。湛知把它做成库里的结构：每份成果记录上游版本和事件截点，依赖是一组带角色的有向无环边，发布走条件更新，历史版本不删除。于是“这份建议当时依据什么”不用靠人回忆，任何一个对象都能在库里回答。导出时再做一次闭包：方案要带上学情版本，班级要带上全部成员版本，微课堂要带上正文版本，缺一环就拒绝出包。4.6 里 799 条证据、缺失 0，就是这个闭包的直接结果。

这套机制还有一个副产品：它让“降级”变成可陈述的事实。包里有 3 份当前方案依赖历史学情，系统把它们标成 `analysis_current=false` 并附上 `basis_warnings`，没有顺手改成最新。评委看到的是一个诚实的版本链，不是一个漂亮的假状态。

### 5.3 答案保护与 fail-closed

学生端最不能出错的地方是答案被提前泄露，这一节讲怎么防。

同一套保护集合在六个通道上复用：题目接口、提示接口、Agent 引导、微课堂引用、证据解析、缓存键。三级提示按层释放，累计内容也要检查；引导回复先做结构比对（同题、轻微改数字的克隆、连起来等价于完整解答），再做独立语义复核；独立检查下的帮助必须先取得学生确认并写进账本。帮助事件只有一个账本，B 判断独立性时读它，不读前端声明。

fail-closed 是同一套思路的另一面。系统在四个位置选择“宁可停下”：模型未配置或超时，保留确定性结果并标注降级，不生成假内容；审核缺项或依据不可解析，停止自动发布；微课堂复核不过，退回已审核模板；导出缺必需版本，返回 422 并列出缺项，不打不完整的包。有些轮次因此看起来“没做完”，但已经交出去的东西都能被核对。

### 5.4 A/B/C/Agent 的协作边界

四个角色怎么分工、为什么不让 Agent 什么都干，这一节回答这两个问题。

| 角色 | 负责 | 不负责 |
|---|---|---|
| A 课程知识 | 知识点、关系、题目与评分点对齐 | 判断学生掌握程度 |
| B 学情与评分 | 指标、诊断、评分、班级分析 | 自建推荐策略 |
| C 策略与方案 | 策略、任务组、提示、微课堂、审核发布 | 创造未登记题目 |
| Agent | 理解意图、查工具、组织解释、准备候选 | 直接写库、绕开审核、替 C 做判断 |

这样切的实际效果是：Agent 越权也拿不到结论。它想改方案，只能生成候选；候选要过 C 的完整审核；审核要过独立复核；发布要过条件更新。教师在对话里说“好的”，系统也只当作一次对话，真正的确认必须落在确认卡上。学生端同理，求助要先确认受助，确认之后才释放引导，而且这一步会被 B 用来判断这次作答算不算独立完成。

### 5.5 微课堂：六类组件、模型与规则双路径

给学生的讲解材料怎么做到既个性化又不出错，这一节讲这条设计。

微课堂的个性化来自三处输入：这个学生错在哪、这个知识点缺什么前置、他手上还有多少时间。C 先按这些输入定讲解目标和长度，再决定用哪种方式生成。模型路径写得更贴合个人错因，规则路径稳、可复现、零成本。两条路径共用同一套组件 schema 和同一套审核，学生看到的界面完全一样，差别只在正文的生成方式和证据标注。

六类组件是这条设计的骨架。封闭的组件集合让数学检查做得动：推导可以逐步比对，正误对照可以验等价，数轴可以精确比较端点和开闭。160 份微课堂里 154 份走规则、6 份走模型，比例不好看，原因是预算有限，能力上并没有缺失：6 份模型生成的正文全部通过八项复核，说明模型路径是通的。

## 6 使用平台、完成方式与数据范围

这一章回答三个交付层面的问题：跑在什么环境上，是怎么做出来的，用了哪些数据、边界在哪。

### 6.1 使用平台

运行环境和依赖列在下面，方便复现和部署。

系统是本地双端 Web 应用，单机启动，不需要容器和外部中间件。

| 项目 | 配置 |
|---|---|
| 操作系统 | Windows 11（Linux 命令已在文档给出，未实机验证） |
| 运行时 | Python 3.12.16，Node.js 与 npm，版本以锁文件为准 |
| 后端 | FastAPI + Pydantic v2 + SQLAlchemy + Alembic，SQLite 单文件库 |

### 6.2 完成方式

这套东西是一步步做出来的，这一节说明节奏和证据。

开发按依赖分阶段推进，每个阶段单独留证据。先是共享契约与数据模型：字段取并集、保留旧接口兼容、迁移可重复执行；再按 A、B、C 的依赖顺序实现业务并各自独立测试，A 的产出是 B 的输入，B 的产出是 C 的输入，任何一段没通过就不向下游放行；然后接 Agent 的受控工具循环，最后接 Web 闭环。每个阶段的测试命令、实际输出、通过数和未通过项都记在仓库的验收对照里，计划中的测试不写成已通过。

这套做法有一个直接后果：进展不均匀。业务链路跑得比交互层远，后端比前端完整，数据比文档细致。第 8 章的限制清单就是这种不均匀的清单，读者不必从文字里猜哪些做了、哪些没做。

### 6.3 数据使用范围

数据从哪来、到哪去、什么不能做，这一节交代清楚。

赛方提供的六张模拟学情 CSV、八份教材切片和课程标准 PDF 只在本机授权范围内使用。系统不使用真实学生个人信息；赛方原始数据不进入公开样例，不作为前端演示数据；演示模式只用明确标记的合成数据，与真实模式共用页面但不共用数据源。模型调用只发送完成任务所需的最小文本片段，外发授权默认关闭，本轮由本机配置显式开启；页面图像和扫描件不在外发范围内。赛后按赛事要求删除本地赛料副本。

## 8 已知限制

这一章如实列出还没做好的地方。写这一章是为了让评委知道边界在哪，答辩时也不会被问住。

| 限制 | 具体表现 | 怎么理解 |
|---|---|---|
| 模型覆盖有预算 | 161 个方案版本中 9 个 hybrid、152 个 rule；160 份微课堂中 6 份 model、154 份 rule；364 条诊断只有 11 条带模型解释 | 规则负责可复现判断，模型在预算内参与生成与复核；没覆盖的部分如实标 rule |
| 6 条历史标签未回写 | 6 份模型生成的微课堂，`source_label` 仍写着“规则模板生成，已审核” | 不回写已发布的 payload；清单单列，展示文案与实际生成方式不一致 |
| 难度、摘要、页码缺位 | 65 条材料难度全为空；87 份学情没有正式摘要；教材没有页码；7 条教材没有关联知识点 | 方案暂时不能按难度精确分层；导出不代算、不填假等级、不编摘要 |
| A 统计当前 payload 是旧值 | 已发布知识仍是 58/54 = 107% 的旧口径；新代码已改成题目、学习卡、教材分开统计 | 重建会把 9 个未核验来源点挤出正式对象，影响 C，故暂不重建 |
| 导出任务首次轮询偶发 404 | 导出 POST 返回 202 后，第一次 `GET /jobs` 返回 404，下一次 200，任务最终成功 | 创建路径的事务提交晚于 202 响应；已定位原因，尚未修 |
| 班级授权按全校教师设定 | Agent 候选列表与审批未按 `allowed_class_ids` 过滤；导出接口接收全数据集名册；当前界面用全校教师会话 | 产品设定为全校教师，直调 API 才触发；已记录为已知限制 |
| 知识关系被预算截断 | 关系推断 180 秒预算，6 批只完成 2 批，保留 11 条、拒绝 5 条、4 批未处理 | 关系是“已核验的子集”，不能当全集读；23 个候选点等教师处理 |
| 教材原文引用缺失 | 160 份微课堂的 `source_refs` 全为 0，只有知识点证据 `evidence_refs` | 微课堂能追到知识点，追不到教材原文；包内标 `evidence_only`，不冒充引用 |
| 版本链含历史依赖 | 3 份当前方案依赖历史学情，6 份微课堂挂历史方案 | 可追溯，依据落在历史版本上；按 `basis_warnings` 和版本链说明解释 |
| 方案目标与预期结果同文 | 159 个任务组的 `goal` 与 `expected_outcome` 完全一致 | 属文案层待细化，不影响活动与发布合法性 |

这些限制不改变已经验证的结论：成果包完整、发布状态真实、D14 与 D17 是修好生成逻辑之后通过的。答辩的口径四句话：规则定值，模型释义并接受独立复核；能核对的写清楚，不能核对的写原因；失败显式停下；已知边界就在这一章。
