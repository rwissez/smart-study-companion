# 07 问题清单与改进路线

## 这一节回答什么

如果我是产品负责人，下一版先改什么、后改什么、怎么判断改好了。

## 分级标准

- P0：不改会破坏用户信任或比赛演示。
- P1：不改会让产品显得不专业，但还能讲完。
- P2：长期产品化问题，不影响当前比赛。

## P0：必须优先

### P0-1 学生画像、方案、对话没有锁死同一个节点

现象：

- 画像取最新学情；
- 方案取最新正式头；
- 对话不带节点；
- 页面可能显示 N01，回答却是 N02。

影响：

- 用户会认为系统“看错学生”；
- 答辩现场一旦出现，很难解释。

修法：

- 页面顶部显示当前学生、节点、版本；
- 画像、方案、对话共用同一个 node 上下文；
- 切换节点时重置对话或明确提示。

工作量：中。

### P0-2 发布状态被 payload 误导

现象：

- 学情 payload 还是 unpublished；
- publications 表已有发布记录；
- 对话/画像可能说“尚未发布”。

影响：

- 用户以为系统没完成分析；
- 导出和页面说法不一致。

修法：

- 所有面向用户的发布状态以 publications 表为准；
- 或者在发布后回写 payload。

工作量：小到中。

### P0-3 最终输出像数据清单

现象：

- 先列 0.20、0.33、5 道、3 道；
- 没有主次；
- 没有“为什么不动其他指标”。

影响：

- 教师看完不知道先做什么；
- 评委觉得“分析呈现”弱。

修法：

- 结论先行；
- 2—3 条关键证据；
- 每个数字带解释；
- 说明证据不足项；
- 给下一次观察点。

工作量：小，主要是提示词和输出结构。

## P1：应该尽快

### P1-1 学生对话像教师报告

- 学生需要“你这道题错在哪、下一步做什么”；
- 不需要“指标、版本、证据状态”的长报告。

修法：角色化输出模板，学生端短答。

### P1-2 Agent 候选确认入口不统一

- Agent 能准备候选；
- 教师审核入口和编辑入口不统一；
- 用户不知道去哪里确认。

修法：统一“待确认方案”入口。

### P1-3 错误提示太技术

- `RESULT_NOT_READY`
- `PLAN_UNPUBLISHED`
- `EXPORT_INCOMPLETE`

修法：页面用人话，技术码放折叠详情。

### P1-4 对话上下文切换不清晰

- 旧对话绑旧节点；
- 切换学生/节点后历史还在；
- 用户以为在问当前对象。

修法：对话标题显示学生/节点，切换时提示“新对话”。

### P1-5 导出首次轮询偶发 404

- 创建导出后任务行未提交，首次查任务 404；
- 下一次正常。

修法：创建导出后先提交任务行，再返回 202。

## P2：产品化

- 账号体系与多租户；
- 班级权限从“全校教师”升级为可配置；
- 模型成本与限流；
- 教材页码与来源精度；
- 难度、摘要、关系全集；
- `model_calls` 审计；
- 旧标签回写；
- 监控与运维。

## 两周行动建议

### 第 1—2 天

- 修 P0-1、P0-2。
- 锁一个演示学生/节点，跑通画像、方案、对话。

### 第 3—5 天

- 重写个人分析提示词，加入 D01 示例。
- 教师端输出改成“结论—证据—动作—边界”。

### 第 6—8 天

- 学生端对话角色化。
- Agent 候选统一入口。
- 错误提示人话化。

### 第 9—10 天

- 用 10 人、20 人两组数据各跑一次。
- 记录证据不足比例、导出成功率、对话错节点次数。

### 第 11—14 天

- 修导出时序、旧标签、A 统计展示。
- 做一次真实教师可用性测试。

## 验收指标

| 指标 | 目标 |
|---|---|
| 画像/方案/对话节点一致率 | 100% |
| 发布状态误报 | 0 |
| 教师读完首段能说出“先做什么” | ≥80% |
| 学生对话平均长度 | ≤300 字 |
| 对话错节点投诉 | 0 |
| 证据点击后能解析 | 100% |
| 导出预检一次通过率 | ≥95% |
| 10—20 人新数据全流程 | 成功 |
| 模型不可用时规则路径 | 可完成 |

## 最终建议

先修“看得对”，再修“说得好”，最后修“铺得开”。

- 看得对：节点、发布状态、版本一致。
- 说得好：结论先行、证据解释、角色化表达。
- 铺得开：账号、权限、多租户、成本、运维。

当前比赛阶段，前两项决定分数，第三项决定故事能不能讲大。
