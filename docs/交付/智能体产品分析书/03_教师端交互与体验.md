# 03 教师端交互与体验

## 这一节回答什么

教师从打开系统到拿到可执行方案，顺不顺；哪些地方像产品，哪些地方像后台。

## 教师的主路径

教师只关心四件事：

1. 这个班怎么样。
2. 这个学生为什么这样。
3. 下一步练什么、怎么排。
4. 能不能把结果交出去。

对应四个入口：

- 班级总览
- 学生画像
- 课程体系
- 数据与成果

再加一个公共入口：AI 对话。

这个信息架构是对的。教师不需要先理解 A/B/C，也不需要知道版本和模型。

## 做得好的地方

### 1. 班级总览先给结论

雷达、薄弱项、掌握分布、重点关注名单先出现，不是先给原始表格。

教师一眼能知道“这个班哪几块不稳、哪些人要优先看”。

### 2. 学生画像有证据抽屉

点开一条结论，能看到：

- 指标分子分母
- 原始作答
- 评分点
- 证据编号
- 版本

这对“可追溯性”很关键，也是赛题最看重的。

### 3. 方案审核不是一键发布

方案有检查、预览、确认，发布前能看到差异和风险。

这比“AI 直接改完就上线”可信。

### 4. 导出有预检

材料缺失、方案未发布、版本不一致，会先拦住，不让你出一个半包。

这是教师真正需要的安全感。

## 体验上的摩擦

### 摩擦一，当前节点不够显眼

教师看班级总览时会切换 N01/N02，但页面里“当前节点”的提示不够强。

学生画像和对话又各自取最新节点。

结果：

- 页面在 N01；
- 对话回答 N02；
- 教师以为系统看错了学生。

这不是算法错，是上下文提示不够。

### 摩擦二，对话回答太长，像报告

教师问“D01 学习情况怎么样”，得到的回答经常是：

- 一级标题、二级标题；
- 多个指标表；
- 大段边界说明；
- 最后才给建议。

教师真正想要的是：

> 这个学生主要卡在哪两件事，先练什么。

现在的回答信息量够，但“先看什么”不够突出。

### 摩擦三，教师理由有模板味

任务组理由经常出现：

> 存在具体错误证据，安排纠错；依据……；选用材料……；学生具体表现：得分率……

信息是对的，但读起来像系统日志。

更好的写法：

> 这个学生在“把少 3 写进括号”上反复出错，先用两道题把数量关系转对，再谈代入求值。

### 摩擦四，Agent 候选的确认路径不够顺

Agent 能准备候选，但候选进入教师审核队列的路径不够统一。

教师可能遇到：

- 对话里生成了候选；
- 页面上找不到确认入口；
- 或者确认入口和原方案编辑入口不是同一个地方。

这会让“智能体改方案”看起来像半成品。

### 摩擦五，错误提示偏技术

例如：

- `RESULT_NOT_READY`
- `PLAN_UNPUBLISHED`
- `EXPORT_INCOMPLETE`

这些对开发有用，对教师不够友好。

理想提示：

> 这个学生这个节点还没有正式学情，先完成分析再导出。

## 教师端最该补的三件事

### 第一，节点和对象始终可见

页面顶部固定显示：

> 当前：D01 · N01 · 2026-11-28 正式版

切换节点时，画像、方案、对话一起切。

### 第二，回答先给“教师行动建议”

对话第一段应该是：

> 先处理“文字关系转代数式”，再做“移项变号”；其余三项证据不足，先不动。

后面再展开证据。

### 第三，把确认入口收成一个

教师不需要知道候选来自 Agent 还是编辑器，只需要一个“待确认方案”入口。

## 教师端评分

| 项 | 评分 | 说明 |
|---|---|---|
| 信息架构 | 4/5 | 四页清楚，符合教师任务 |
| 首屏结论 | 4/5 | 班级总览和画像有重点 |
| 证据可查 | 4.5/5 | 抽屉和版本做得扎实 |
| 方案审核 | 3.5/5 | 有审核，但 Agent 候选入口不统一 |
| 对话可用 | 3/5 | 能答，但太长、节点不稳 |
| 错误提示 | 3/5 | 技术码多，人话少 |
| 整体 | 3.7/5 | 能用，离“顺手”还有一段 |

## 本维度结论

教师端是湛知最成熟的一面。

它已经能做到“看班、看人、看方案、导出”的闭环，但还没有做到“任何页面都知道自己在看哪个学生、哪个节点、哪个版本”。

这不是功能缺失，是产品细节没有收口。
