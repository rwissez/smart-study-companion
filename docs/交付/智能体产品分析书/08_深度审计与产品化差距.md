# 08 深度审计与产品化差距

## 这一节回答什么

前面的产品分析回答“能不能用、顺不顺、像不像智能体”。这一份往下追一层：如果要把湛知从比赛原型变成可试点、再变成可交付的产品，每个环节现在到底卡在哪，卡得有多深。

## 审计口径

先区分三种“达标”：

1. **比赛达标**：能演示、材料完整、证据可核、答辩讲得清。
2. **试点达标**：一个学校、一个班、少量教师能安全使用，出问题能恢复。
3. **产品化达标**：多学校、多角色、可运维、可计费、可审计、可支持。

湛知目前的位置：

| 层级 | 判断 |
|---|---|
| 比赛达标 | 基本达到 |
| 试点达标 | 部分达到，缺账号、隔离、运维 |
| 产品化达标 | 未达到 |

## 一页评分卡

| 领域 | 当前分 | 比赛要求 | 试点要求 | 产品化要求 |
|---|---:|---|---|---|
| 智能体定义与能力 | 3.5/5 | 工具型智能体可接受 | 上下文稳定、失败可恢复 | 可评估、可监控、可持续学习 |
| 教师端交互 | 3.7/5 | 四页闭环可演示 | 低培训成本、错误可读 | 可配置、可批量、可协作 |
| 学生端交互 | 3.4/5 | 本人数据可看可学 | 节点清晰、语气适龄 | 多端、提醒、家长/教师协同 |
| 输出可理解性 | 3.0/5 | 证据可核 | 结论先行、角色分层 | 可定制、可多语言、可审计 |
| 数据与独立评测 | 3.5/5 | 15 人干跑可讲 | 10—50 人稳定 | 多批次、多学校、多版本 |
| 工程与部署 | 3.0/5 | 本机可跑 | 单校可运维 | 多租户、高可用、可升级 |
| 安全与合规 | 3.5/5 | 模拟数据、权限基本正确 | 账号、审计、保留策略 | 等保/隐私/模型外发治理 |
| 产品运营与支持 | 2.0/5 | 文档和演示够 | 培训、反馈、值班 | 客户成功、计费、SLA |

## 二、智能体定义与能力

### 现状证据

- 有工具调用：学情、方案、班级、微课、证据查询。
- 有任务路由和最多 6 步的受控编排。
- 有写操作确认，不能直接发布。
- 有事实核查和失败降级。
- 真实测试里，D01 能生成三段式案例；DC01、DC02 能生成单班共性分析。

### 产品化要求

智能体不能只会“答一次”，还要满足：

- 同一个学生、节点、版本在画像、方案、对话里一致。
- 工具失败时能说明失败原因，不静默改答案。
- 跨班比较这类常见任务要能一次完成。
- 用户能看见“系统方案”和“模型建议”的区别。

### 关键缺口

| 缺口 | 严重度 | 证据 |
|---|---|---|
| 节点上下文不统一 | 高 | 问 D01 曾回答 N02；画像、方案、对话各自取最新 |
| 发布状态误报 | 高 | D01 输出说方案未发布，正式发布记录存在 |
| `compare_classes` 工具失败 | 中高 | 跨班比较调用返回策略失败，只能分两次单班跑 |
| 模型建议与正式方案混写 | 中 | D01 建议先移项，正式方案先列式 |
| 长期记忆弱 | 中 | 会话有历史，跨会话偏好和教学风格没有沉淀 |
| 主动行动缺失 | 低 | 不主动巡班、不主动提醒，靠用户先问 |

### 结论

比赛够用，试点不够稳。

试点前必须解决“三个一致”：学生一致、节点一致、发布状态一致。否则教师不会信任它。

## 三、教师端交互

### 现状证据

- 班级总览、学生画像、课程体系、数据与成果四页闭环。
- 证据抽屉、版本、预检、导出都有。
- 方案有审核，不是一键发布。

### 产品化要求

- 教师第一次用，30 分钟内能完成一次“看班—看人—调方案—导出”。
- 任何页面都能看到当前数据集、节点、版本。
- 错误提示能直接告诉教师下一步做什么。
- Agent 候选和人工编辑走同一个待确认入口。

### 关键缺口

| 缺口 | 严重度 | 说明 |
|---|---|---|
| 顶部上下文条不完整 | 高 | 节点、版本、发布状态没有始终可见 |
| 对话回答过长 | 中高 | 教师需要先看结论，不是先看指标表 |
| 错误码偏技术 | 中 | `RESULT_NOT_READY`、`EXPORT_INCOMPLETE` 直接露出 |
| Agent 候选入口不统一 | 中 | 对话生成候选后，教师不知道去哪确认 |
| 批量操作弱 | 低 | 多学生调整、批量导出还不顺 |

### 结论

教师端是产品最成熟的一面，但“上下文可见”和“候选收口”不解决，试点时会被教师当成“功能很多但不敢用”。

## 四、学生端交互

### 现状证据

- 学生只看本人，越权返回 403。
- 计划按任务组顺序排。
- 三级提示，不直接给答案。
- 微课堂有六类组件。

### 产品化要求

- 学生打开就知道“现在在哪个节点、第几组、做什么”。
- 对话像对本人说话，不是教师报告。
- 卡住时能锁定当前题目求助，而不是泛泛问答。
- 家长或教师能看到学生使用情况和风险提示。

### 关键缺口

| 缺口 | 严重度 | 说明 |
|---|---|---|
| 学生画像不显示当前节点 | 高 | 学生不知道看的是哪次分析 |
| 对话不带节点/活动 | 高 | 可能答成另一个节点，或泛泛而谈 |
| 对话语气偏教师 | 中高 | 一上来指标、版本、证据状态 |
| 发布状态误报 | 高 | 学生看到“尚未发布”会以为系统坏了 |
| 家长/教师协同缺失 | 低 | 不是比赛必需，但影响试点 |

### 结论

学生端能学，但还不“懂我”。试点前至少要做到“节点可见、对话适龄、求助锁题”。

## 五、输出可理解性

### 现状证据

- 指标有分子分母，证据能回到原句。
- 证据不足会标 insufficient。
- 真实模型输出能生成案例文字。
- 但输出仍常以指标清单开头，教学建议有模板句。

### 产品化要求

- 教师三十秒知道“先做什么”。
- 学生三十秒知道“我错在哪、下一步做什么”。
- 评委三分钟能核一条结论。
- 任何数字都能回答“所以呢”。

### 关键缺口

| 缺口 | 严重度 | 说明 |
|---|---|---|
| 结论不先行 | 高 | 先列指标，后给判断 |
| 数字没有解释 | 高 | 0.20、0.33、5 道并列，读者不知道主次 |
| 角色不分开 | 高 | 教师、学生、评委拿到同一种报告 |
| 模板句重复 | 中 | “存在具体错误证据，安排纠错”像日志 |
| 证据不足项沉默 | 中 | 只写要练的，不写为什么不动的 |

### 结论

可解释性的底子很好，表达层拖了后腿。改提示词和输出结构，投入小、收益大。

## 六、数据与独立评测

### 现状证据

- 40 人、806 条记录的全量回归跑通。
- 15 人、252 条记录的临时库干跑成功。
- 6.46 秒完成规则路径，30 份学情、30 份方案、60 份微课堂。
- 没有教材 PDF 时只有 9 个指标级知识点、0 条关系。

### 产品化要求

- 10 人、20 人、单班、无记录学生等边界都有结果。
- 不同教材覆盖下，知识图谱退化有明确提示。
- 导入失败有可恢复路径，不是只报 400。
- 数据版本、来源、授权能追溯。

### 关键缺口

| 缺口 | 严重度 | 说明 |
|---|---|---|
| 只做了 15 人一种规模 | 中高 | 10 人、20 人、单班、无记录学生未系统验证 |
| 教材覆盖不均 | 中高 | 28 个教材点集中在 T03，7 份材料无知识点 |
| 小样本阈值偏保守 | 中 | 125 条发现中 93 条证据不足 |
| 文件上传限制 | 中 | 12 文件、32MB；多切片要调配置 |
| 模型不可用时质量下降 | 中 | 规则可跑，但表达和诊断退化 |

### 结论

“换数据能跑通”成立，“任意数据都能完整覆盖”不成立。

比赛可以讲边界，试点必须把边界做成产品提示，而不是让教师自己猜。

## 七、工程与部署

### 现状证据

- 本机 FastAPI + React + SQLite。
- 启动器、迁移、备份脚本都有。
- 单机单租户，没有账号体系。
- 前端默认真实 API，不是 demo。

### 产品化要求

- 安装、升级、回滚可重复。
- 数据备份、恢复、迁移有演练。
- 多学校/多班级隔离。
- 监控、日志、告警、限流。
- 模型密钥和成本可控。

### 关键缺口

| 缺口 | 严重度 | 说明 |
|---|---|---|
| 无账号/SSO | 高 | 试点必须接学校身份 |
| 无多租户隔离 | 高 | 当前是单库单校 |
| SQLite 单文件 | 中高 | 并发、备份、扩容受限 |
| 无监控告警 | 中高 | 任务失败只能看日志 |
| 模型成本无计量 | 中 | 有预算限制，无账单/限额 |
| 部署依赖手工 | 中 | Python、Node、迁移、模型配置都要人 |

### 结论

比赛和单机试点可用，学校生产部署不够格。

## 八、安全与合规

### 现状证据

- 学生只读本人，越权 403。
- 教师写操作需确认。
- 模拟数据，无真实学生个人信息。
- 模型外发有授权开关。

### 产品化要求

- 正式账号、角色、班级授权。
- 操作审计、数据访问审计。
- 数据保留、删除、导出策略。
- 模型外发内容可解释、可关闭、可追溯。
- 密钥不落前端、不进日志。

### 关键缺口

| 缺口 | 严重度 | 说明 |
|---|---|---|
| 无正式身份体系 | 高 | demo session 不是账号 |
| 教师班级授权是全校范围 | 中高 | 赛题不要求，试点会要求 |
| 审计不完整 | 中 | 有工具轨迹，缺统一操作审计 |
| 数据保留策略缺失 | 中 | 没有自动清理/导出/删除流程 |
| 模型外发治理不完整 | 中 | 有开关，缺逐次登记和用户可见说明 |

### 结论

当前安全边界对比赛够用，对学校试点还需要一层身份、审计和数据治理。

## 九、产品运营与支持

### 现状证据

- 有 README、部署文档、功能说明书、演示脚本。
- 有失败案例和已知限制。
- 没有培训体系、客户成功、值班、SLA。

### 产品化要求

- 新教师 30 分钟上手。
- 常见问题有自助答案。
- 出问题有人响应。
- 版本更新有说明和回滚。

### 关键缺口

- 无培训材料的分层版本。
- 无使用数据回流。
- 无支持工单和 SLA。
- 无版本发布节奏。

### 结论

这是最容易被忽略、但最影响试点续约的一块。

## 十、总体判断

### 比赛

可以交。

- 三项任务有真实产出。
- 证据链完整。
- 质量门有真实失败案例。
- 文档和案例齐全。

### 试点

可以试，但要先补四件事：

1. 节点、发布状态、版本三个一致。
2. 学生端对话适龄和锁题。
3. 账号、班级授权、备份恢复。
4. 监控和模型成本。

### 产品化

还早。

- 多租户、SSO、LMS 对接、审计、SLA 都没有。
- 不是再改几个提示词能解决的，是产品架构和运营体系问题。

## 十一、最该先修的顺序

1. 信任：节点、发布状态、版本一致。
2. 表达：结论先行、角色分层。
3. 稳定：工具失败、上传限制、导出时序。
4. 试点：账号、授权、备份、监控。
5. 规模化：多租户、SSO、成本、合规。

前三项决定比赛和试点能不能成，后两项决定能不能变成产品。
