## 一 技术基线（已定，不再讨论）

React + TypeScript + Vite + npm。路由React Router，服务端状态TanStack Query，图表Recharts，样式CSS Modules。目录`frontend/`。

两条硬规则：

1. **不手写第二份契约。** `npx openapi-typescript contracts/openapi.json -o src/api/types.ts`生成类型，所有请求响应类型从它导入。后端改契约 → 重新生成 → TypeScript报错 → 这就是前后端不一致的检测机制。手抄的interface会让这套机制失效。
2. **只调相对路径`/api/v1/...`。** 开发期由Vite proxy转发到`http://127.0.0.1:8000`，生产期前端由后端同源托管。代码里不出现`http://127.0.0.1:8000`，否则换端口就全挂。

```ts
// vite.config.ts
server: { proxy: { '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true } } }
```

## 二 对接接口

A0-b已可调用的全部接口。`{{base}} = /api/v1`，除`/health`外均需`Authorization: Bearer <token>`。

| 方法 | 路径 | 用途 | 可见角色 |
|---|---|---|---|
| GET | `{{base}}/health` | 启动自检，**无需令牌** | 全部 |
| POST | `{{base}}/demo-sessions` | 创建演示会话，换取令牌 | 全部 |
| GET | `{{base}}/datasets` | 数据集列表 | 教师 |
| GET | `{{base}}/datasets/{dataset_id}/runs` | 某数据集的分析运行列表 | 教师 |
| GET | `{{base}}/catalog` | 知识点与指标体系 | 教师、学生 |
| GET | `{{base}}/materials/{material_id}` | 单条学习材料 | 教师、学生（字段不同） |
| POST | `{{base}}/chat` | 对话（当前未配置模型时503） | 教师、学生 |

### 2.1 启动自检 `GET /api/v1/health`

**前端启动后的第一个请求，在渲染任何业务页面之前。**

```json
{ "status": "ok", "app_version": "0.1.0", "schema_version": "1.0",
  "database_ok": true, "demo_mode": true, "model_configured": false }
```

四个字段直接决定UI能力，D必须按它们分支，不要硬编码假设：

- `database_ok=false` → 全站不可用，显示"服务未就绪"
- `demo_mode=false` → **不渲染身份选择入口**（此时`/demo-sessions`返回404）
- `model_configured=false` → 对话入口置为不可用并说明"模型服务尚未配置"，**不要**让用户点进去再吃503
- `schema_version`与前端生成类型时的版本不一致 → 顶部显示提示，不阻断

### 2.2 创建会话 `POST /demo-sessions`

这是**本地角色模拟，不是登录**，没有密码。三种请求：

```jsonc
{ "role": "teacher" }                                        // 引导态教师：还没选数据集
{ "role": "teacher", "dataset_id": "ds_xxx" }                // 绑定态教师
{ "role": "student", "dataset_id": "ds_xxx", "student_id": "D04" }
```

201响应：

```json
{ "session_token": "<仅此一次返回的明文>", "expires_at": "2026-11-20T09:00:00Z",
  "scope": { "session_id": "...", "role": "teacher", "dataset_id": "ds_xxx",
             "student_id": null, "bootstrap": false,
             "capabilities": ["list_datasets", "view_class_analysis", "..."] } }
```

**令牌只在创建时返回一次，服务端只存哈希。** 刷新页面后令牌丢失是预期行为，此时回到身份选择页重新创建会话即可——不要为了"保持登录"把令牌写进localStorage，那是把演示态当成生产认证。会话12小时过期。

典型流程：`role=teacher`（引导态）→ `GET /datasets` → 用户选一个 → 再`POST /demo-sessions`带`dataset_id` 换一个绑定态令牌 → 丢弃旧令牌。

### 2.3 能力集：前端的路由守卫

`scope.capabilities`是**权威来源**，D的菜单与路由守卫按它判断，不要用`role === 'teacher'`这类字符串比较（引导态教师也是teacher，但只有3项能力）。

| 身份 | capabilities |
|---|---|
| 引导态教师 | `list_datasets`, `import_dataset`, `select_dataset` |
| 绑定态教师 | 上面3项 + `view_class_analysis`, `view_student_analysis`, `view_curriculum`, `view_quality`, `edit_recommendations`, `export_run`, `chat_teacher` |
| 学生 | `view_own_analysis`, `view_own_plan`, `chat_own` |

对话的能力名按角色区分：`/teacher/chat`守`chat_teacher`，`/student/chat`守`chat_own`。两者打的是同一个`POST /chat`，由服务端按会话角色判定，前端不必也不应传角色参数。引导态教师没有`chat_teacher`，所以选数据集之前对话入口不可用。

守卫的意义是**少发注定被拒的请求、少渲染点不动的按钮**，不是安全边界。真正的边界在服务端：学生会话请求他人数据返回`NOT_FOUND`（不是403——故意不暴露名册里有谁），学生拿到的`/materials/{id}`已被服务端删去`reference_answer`、`reference_explanation`、`rubric_points`、`reviewed_variant_tag`四个字段。**前端不得自行实现"隐藏答案"逻辑**，那只是视觉遮挡。

### 2.4 列表类接口

`GET /datasets` → `{ items: [{ dataset_id, status, created_at, parent_id, synthetic, student_count, table_row_counts }], total }`

`synthetic=true`的数据集，界面上**必须有可见标识**（合成数据不能被误当成真实赛事数据来解读）。

`GET /datasets/{id}/runs` → `{ items: [{ run_id, dataset_id, catalog_version, rule_version, status, created_at }], total }`

`run_id`是后续所有分析接口的必带参数。界面上要让"当前正在看哪一次运行"始终可见——**同一数据集的两次运行结果可能不同，截图离开上下文就无法解释**。

### 2.5 `GET /catalog` 与 `GET /materials/{id}`

`/catalog` → `{ catalog_version, topics, indicators }`，是所有ID到名称的翻译表。建议进程内缓存一次，`staleTime: Infinity`——它在一个会话里不变。界面上不要出现裸ID（`N01`、`I03`、`T02`），一律翻成名称。

`catalog_version`省略时服务端取会话数据集的最新版本；显式传入时会校验归属，不属于本数据集则`NOT_FOUND`。

下面这些**现在还没有**，B/C在A1实现。D可以先按形状写query hooks与mock，接口到位后只换URL：

| 方法 | 路径 | 返回 |
|---|---|---|
| GET | `{{base}}/runs/{run_id}/class-results` | `ClassResult[]` |
| GET | `{{base}}/runs/{run_id}/students/{student_id}/results` | `StudentResult` |
| GET | `{{base}}/runs/{run_id}/students/{student_id}/recommendations` | `Recommendation[]` |

## 三 协议

### 3.1 响应信封

**所有**接口的响应都是这两种形状之一，没有例外：

```jsonc
// 成功
{ "schema_version": "1.0", "request_id": "req-ab12...", "data": { ... }, "warnings": [] }
// 失败
{ "schema_version": "1.0", "request_id": "req-ab12...",
  "error": { "code": "NOT_FOUND", "message": "未找到该学生", "details": [] } }
```

封装一个`request<T>()`：拆信封、成功返回`data`、失败抛携带`code`与`request_id`的`ApiError`。**业务组件不碰信封**，只拿`data`。

`warnings`是数组，成功时也可能非空，含义是"结果可用但有前提"（如"4条记录因异常被排除"、"模型文本未预生成，当前为规则结果"）。**必须展示**，不要丢弃——它是本项目"结论可追溯"的一部分，答辩时评委大概率会问数据里的异常怎么处理的。

### 3.2 `request_id`

每个响应头与响应体都带`X-Request-ID`。前端可以在请求头主动传入（≤64字符），服务端原样回传；不传则服务端生成。

**错误提示UI里要显示`request_id`**。四个人联调时，"报错了"没法查，"req-ab12cd34报错了"能在服务端日志里一秒定位。

### 3.3 错误码

`error.code`是分支依据，**不要解析`message`文案**（文案会改）。

| code | HTTP | 前端动作 |
|---|---|---|
| `VALIDATION_ERROR` | 400 | 按`details[{field, reason}]`定位到表单项 |
| `UNAUTHORIZED` | 401 | 回身份选择页 |
| `FORBIDDEN` | 403 | 令牌缺失/能力不足；多为前端守卫漏判，回身份选择页 |
| `NOT_FOUND` | 404 | 资源不存在**或无权访问**（二者不可区分，文案不要写"无权限"） |
| `CONFLICT` / `REVISION_CONFLICT` | 409 | 并发编辑；提示"已被更新，请刷新后重试"，**不要静默覆盖** |
| `RESULT_NOT_READY` | 409 | 分析未完成；可轮询重试 |
| `UNPROCESSABLE` | 422 | 数据不满足业务前提 |
| `MODEL_NOT_CONFIGURED` | 503 | 显示"模型服务尚未配置"，**不重试** |
| `SERVICE_UNAVAILABLE` | 503 | 可重试一次 |
| `INTERNAL_ERROR` | 500 | 显示`request_id`并提示查看服务端日志 |

重试策略：只对503且非`MODEL_NOT_CONFIGURED`、以及`RESULT_NOT_READY`重试；4xx一律不重试（TanStack Query默认重试3次，**必须改掉**，否则一个400会打三遍）。

服务端不返回堆栈与绝对路径，所以错误体里没有可供用户自行排查的信息——这是刻意的，不要试图展示更多。

### 3.4 Query Key 约定

缓存键必须包含**会话、运行、学生/班级、节点**四类维度，否则切换身份或运行后会读到上一个的缓存：

```ts
['student-results', sessionId, runId, studentId, nodeId]
['class-results',   sessionId, runId, classId,   nodeId]
['catalog',         sessionId, catalogVersion]
```

切换会话时`queryClient.clear()`。

### 3.5 其他约定

- 请求与响应均`application/json; charset=utf-8`
- 时间一律ISO 8601 UTC带`Z`，展示时转本地时区，**不要**把服务端时间当本地时间直接渲染
- `null`与缺省不同义：`student_id: null`表示教师会话，不是"学生未知"
- 对话历史由服务端持久化，前端不做本地会话存储
- 分页当前统一`{items, total}`，数据量小，A0不做分页控件

## 四 大致需要的功能

九条固定路由（已定，D可增不可改名）：

| 路由 | 身份 | 用途 |
|---|---|---|
| `/` | 全部 | 身份与数据集选择 |
| `/teacher/classes` | 教师 | 班级整体分析 |
| `/teacher/students/:studentId` | 教师 | 单个学生分析 |
| `/teacher/curriculum` | 教师 | 教学序列与材料 |
| `/teacher/chat` | 教师 | 对话 |
| `/teacher/data` | 教师 | 数据导入、运行管理、质量问题、导出 |
| `/student/home` | 学生 | 自己的学习概览 |
| `/student/plan` | 学生 | 自己的练习计划 |
| `/student/chat` | 学生 | 对话 |

每个页面都必须处理的四种状态，**这是本项目的评分点所在，不是工程洁癖**：

1. **加载中**
2. **正常**
3. **错误**（显示`code`含义与`request_id`）
4. **证据不足**——`finding.evidence_status`为`insufficient`时，显示的是"记录不足以判断"，**不是0分、不是空白、不是"未掌握"**

第4种必须单独设计。数据里真实存在D17这类只有4条记录、两个主题零记录的学生，把它渲染成0或空白等于在界面上造假。界面上应当能看出"这里没有结论，是因为没有证据"。

全局必须可见的三件事：**当前身份、当前数据集、当前运行**。这三样决定了屏幕上所有数字的含义，截图脱离它们就无法解释。

## 五 适合老师多元化分析的功能

这一节给**维度与口径**，不给页面。D据此brainstorm具体呈现方式。下面每条的数据依据来自13号文档对真实赛事数据的统计。

### 5.1 五个分析维度

| 维度 | 粒度 | 数据支撑 |
|---|---|---|
| 班级横向 | 班级×指标 | DC01 21人、DC02 19人，可做班际对照 |
| 学生纵向 | 学生×指标×节点 | 40名学生 |
| 知识点 | 节点×指标 | N01 27题、N02 45题，指标覆盖不重叠 |
| 过程性 | 修订、耗时、提示使用 | 799条作答事件、7条二次修订 |
| 数据质量 | 运行级 | 4条待隔离记录、5条未作答、4条待批改 |

### 5.2 必须守住的三条口径（不守住会在答辩被问倒）

**一，N01与N02不能直接比总分。** 两个节点的指标覆盖不重叠，题量27对45。唯一成立的跨节点比较是那40组"同一学生同一题目"的配对。界面上如果把两个节点的得分率并排画成柱状图，是在比较两个不同的东西。要么只在节点内比，要么明确标注"仅配对题目可比"。

**二，证据充足度随粒度剧烈变化。** 学生×指标粒度上只有约34%的格子证据充足；收到学生×主题粒度，充足率约93%。所以**默认粒度建议用主题，指标粒度作为下钻**，并且下钻时必须显示证据量。否则默认视图里三分之二的格子是"不知道"，老师会误读成"没掌握"。

**三，分母必须可见。** 所有比率同时给`numerator/denominator`。"得分率60%"在分母是5和分母是45时是完全不同的两件事。`Metric`里已经带了这两个字段，用上它。

### 5.3 建议具备的能力（D自行决定形态）

- **从结论下钻到证据**：每个`Finding`带`evidence_refs`，指向具体的作答记录、指标或材料。老师看到"该生在某指标表现待加强"应当能点进去看到是哪几道题、哪一步丢分。**这是本项目与普通成绩统计最本质的差别，优先级最高。**
- **共性问题**：班级层面哪几个评分点丢分率最高。数据支撑：解答题丢分率随步骤递增，P1约0.25、P2约0.42、P3约0.67，"后续步骤断掉"是真实共性问题。
- **分层**：同一班级内按证据充足且表现待加强、表现较好、记录不足分组。注意"记录不足"是**独立的一组**，不能并进"待加强"。
- **过程而非只看结果**：修订次数、是否用了提示、作答耗时。7条二次修订量少但是典型案例，可单独呈现。
- **异常与排除的透明化**：4条待隔离记录（含D16一条142%的得分异常）被排除在统计外，界面上要能看到"排除了哪些、为什么"。`Metric.excluded_event_count`与`warnings`就是干这个的。**把异常藏起来比不处理更糟。**
- **三个典型学生的完整链路**：D04（部分得分，11道解答题、7道部分得分）、D14（表现较好）、D17（记录不足）。这三个贯穿演示，能完整走通这三条链路，演示就成立。
- **教师可修改建议**：`Recommendation`带`review_status`（draft/validated/needs_review）与`generation_method`（rule/model），教师编辑走乐观锁。**系统生成的与教师确认过的必须在界面上可区分**——这直接对应"教师主导、AI辅助"的定位。

### 5.4 明确不做

不做实时大屏、不做炫酷动画、不做全局搜索、不做多数据集同屏对比、不做移动端适配。本地演示，一块屏幕，三条链路讲清楚即可。
