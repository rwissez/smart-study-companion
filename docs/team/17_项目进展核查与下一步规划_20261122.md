## 二 新增能力：库管理与可靠性依据

用户新增两项要求，按“可视化修改库存”和“可靠性依据处理”落地。先定义概念，避免各人理解不一。

### 2.1 “库”指什么

| 库 | 内容 | 现有对应 | 要新增的 |
|---|---|---|---|
| 数据集库 | 一次上传的六张 CSV 形成不可变 `dataset_id`；可有父快照 | `datasets`、`source_rows` 表 | 上传、预览、质量报告、设为当前、归档 |
| 目录与材料库 | 指标、题目、学习卡、教材条目、必要联系、变式标注 | `catalogs`、`indicators`、`materials` 表（绑定在 `dataset_id` 上） | 可视化编辑、版本化保存、来源核对状态 |

**可视化修改的原则**：已有数据集和已发布的目录版本**不原地修改**（01号文档：快照不可变；分析缓存键含 `catalog_version`）。所有编辑产生**新版本**（新 `catalog_version`，`parent` 指向旧版），旧运行仍可回看。这样“用户可上传自主数据库”“可视化修改库存”才不会破坏已有结果的可复核性。

13号文档第三节已建议：**目录 = 导入的两张 CSV + 一份由A维护的覆盖层**（键为 `material_id` / `indicator_id`）。本规划沿用，并让覆盖层成为“可视化修改”的存储对象：用户在界面改的内容落成覆盖层的一个新版本，而不是改原始 CSV。覆盖层里没有的新编号降级为“未标注”，相关证据判不足，不报错。

### 2.2 “可靠性依据”指什么

项目里有三类可靠性，分别对应已有字段，**优先复用，不另造一套**：

| 可靠性对象 | 已有字段 | 缺口 |
|---|---|---|
| ① 数据可靠性（作答记录能否进统计） | `QualityIssue.severity/action`、`AnswerEvent.disposition`、`Metric.excluded_event_count` | 无；B 已实现，缺界面和上传后的展示 |
| ② 来源可靠性（材料、页码、联系是否核对过） | `SourceLocator.verification_status`（verified/unverified）、`CatalogLink.basis`（standard/textbook/team_inference） | 缺“谁核对、何时、核对到哪一页”的记录；无编辑入口 |
| ③ 结论可靠性（证据是否足够） | `Finding.evidence_status`（sufficient/insufficient/conflicting）、`limitations` | 13号文档指出现有阈值会让指标层几乎全判“不足”，规则待改 |

**统一处理规则（各模块遵守，具体实现自定）**：
1. 来源为 `unverified` 的材料可以展示，但**不能作为建议的唯一依据**，建议和导出里要带“未核对”标记（C 的 `validate_recommendations` 增加该检查）。
2. `basis=team_inference` 的联系必须在界面和导出里标明“团队推断”，不得写成课标原文。
3. 用户上传的自有数据，来源默认 `unverified`、`synthetic` 按上传者声明；系统不替用户判断真伪，只做**结构校验与质量检查**，并把结果如实展示。
4. 可靠性不足时输出“证据不足/未核对”，不输出确定性结论，也不用颜色暗示“低分”。

> 需要队长确认：核对记录（核对人、时间、页码、备注）新增为一张表 `source_reviews`，还是放进目录覆盖层 JSON。建议前者，便于界面查询和审计；这是对11第三节的补充，由A决定后更新08。

## 三 代码边界（本轮重新划定）

### 3.1 依赖方向（沿用13号文档 §4.1，现补测试强制）

```text
api ─┬→ agent ─→ tools ─┬→ analysis.service       (B，纯函数)
     │                  └→ recommendation.service (C，纯函数)
     ├→ library（新，A：数据集库/目录库仓储与版本）
     ├→ curriculum（新，A：目录构建与覆盖层）
     ├→ db（仓储）
     └→ exports
analysis、recommendation → 只依赖 contracts，不导入 db、api、agent、library
library、curriculum → 依赖 contracts、db，不依赖 analysis/recommendation 的内部实现
contracts → 不依赖任何其他包
```

新增 `tests/contracts/test_import_boundaries.py` 扫描上述规则，违反即失败（A，0.5小时）。

### 3.2 谁能改什么

| 区域 | 唯一修改者 | 其他人如何参与 |
|---|---|---|
| `contracts/`、`migrations/`、`db/`、`api/`、`library/`、`curriculum/`、`agent/`、`exports/`、`config.py` | A | 提出字段/表需求，写明用途与示例，由A合入 |
