## 1. 讨论与维护原则

-   每轮围绕一份设计文档一次提出全部必要提案，逐一确认；向用户通俗说明，面向
    DSH 的技术文档详细严谨，设计负责人负责技术自审。
-   只有双方明确达成一致的内容才列入已确定设计；建议不自动视为决议。
-   每次达成新决议后，在对话中实际更新本记录；未解决的问题保留在待讨论清单中。
-   最终将原始总设计与已确认决议整合为新版总设计，区分已有代码与待开发功能。

## 2. 已确定的设计

### D-001：C 模块与 Agent 的职责划分

**状态：已确认**

上传基本数据并完成必要的课程梳理与学情分析后，C 根据 A、B
提供的结果自动生成每名学生的初始学习方案，包括：

-   文字形式的学习建议；
-   具体题目推荐。

教师若认为方案不合适，可以手动修改，也可以通过与 Agent
对话提出调整要求。

Agent 负责理解教师意图、调用 C 调整方案，以及根据 A、B、C
的相关结果解释学习建议及调整原因。C
负责策略制定、材料推荐及修改后方案的合理性校验。Agent 不另行建立一套与 C
相互冲突的策略制定机制。

\*\*设计理由：\*\*避免职责重叠，充分复用 C
的现有能力，同时保留智能体作为自然语言操作入口的价值。

### D-002：Agent 修改范围

**状态：原则已确认，具体实现待讨论**

当教师要求修改某名学生的学习建议时，Agent
只能修改该名学生的学习方案，不能修改其他学生的方案或超出教师指定范围的数据。

权限限制采用 D-005 确定的双层机制。查询与修改权限的总体规则见
D-006；具体权限校验和批量操作规则仍待讨论。

\*\*示例：\*\*教师要求减少学生甲的方程练习量，调整只应作用于学生甲，不应改变学生乙的方案。

### D-003：学习方案自动审核与发布

**状态：已确认**

C
生成的学习方案不需要教师逐份审核。系统应先自动审核，审核通过后自动向学生发布；仅自动审核不通过的方案需要教师介入审核。

\*\*设计理由：\*\*降低教师处理大量个性化学习方案的工作负担，同时避免不合格方案直接发布。

自动审核的具体标准、失败后的修正流程、教师手动修改或通过 Agent
修改后的审核与发布细节，尚待明确。

### D-004：学习方案动态更新机制

**状态：已确认（总体机制）**

以阶段性更新为主、异常情况下提前更新为辅。正常情况下，学生完成一组学习任务后，由
B 结合新作答记录更新学情，C
据此判断并调整后续学习方案；若出现连续答错、反复请求提示等异常情况，可提前触发分析和调整，不必等待整组任务结束。避免每次作答都重新制定整个方案。

\*\*设计理由：\*\*兼顾及时适应学生学习情况与学习安排的稳定性。

任务组划分、异常触发阈值、学情更新粒度及调整后的审核发布细节尚未确定，分别纳入
P-007、P-008、P-003 继续讨论。

### D-005：Agent 权限双层约束

**状态：已确认（总体原则）**

该原则适用于整个 Agent 模块，而非仅学习方案修改：

-   提示词负责引导 Agent 理解操作范围及允许和禁止的行为。
-   程序强制执行权限和操作范围校验；即使 Agent
    理解错误，也不得越权访问或修改数据。
-   例如，教师要求修改学生甲的学习方案，程序将修改范围限定为学生甲，并拒绝针对学生乙的修改请求。

\*\*设计理由：\*\*提示词不能作为可靠的权限保障，重要限制必须由程序兜底。

角色查询与修改权限总体规则见
D-006；对象锁定方式、批量操作规则、权限校验接口和提示词内容仍待 P-002
细化。

### D-006：查询权限与修改权限分离

**状态：已确认（总体规则）**

\| 用户 \| 查询权限 \| 修改权限 \| \| \-\-- \| \-\-- \| \-\-- \| \| 教师
\| 所负责班级的所有学生 \| 本次明确指定的学生及内容 \| \| 学生 \|
自己的学情、学习方案及允许访问的学习资料 \|
不允许直接修改学情分析及正式学习方案 \|

教师要求参考学生乙的学情调整学生甲的方案时，在两人均属于教师授权范围的前提下，Agent
可以查询两人的学情，但只能修改学生甲的方案。查询和修改权限均须由程序校验。

\*\*设计理由：\*\*支持合理的信息查询与比较，同时严格控制数据修改范围。学生正常提交作答记录与系统自动更新学情并不等于学生直接修改正式分析或方案。

### D-007：Agent 修改前的确认机制与撤销

**状态：已确认（总体规则）**

-   指令明确、修改对象与内容清晰的单人操作，可直接执行，无需重复询问教师，但仍须通过权限与合理性校验。
-   指令有歧义或修改内容未明确时，Agent
    先提出具体修改方案，待教师确认后执行。
-   涉及批量修改时，先明确涉及的学生和修改范围，经教师确认后执行，不得超出授权范围。
-   所有修改保留历史版本，支持教师撤销。

**示例：**"将学生甲的练习量减少至 3
道题"可直接执行；"帮学生甲调整一下学习方案"须先提出调整方案；"给成绩较差的学生减少练习量"须先明确学生名单并确认。

\*\*设计理由：\*\*兼顾操作效率与安全，防止模糊指令或批量操作造成意外修改。具体确认交互、撤销机制及修改后的审核发布流程分别留待
P-002、P-009、P-011、P-003 细化。

### D-008：Agent 任务识别与自主拆解

**状态：已确认（总体原则）**

Agent
应识别用户意图和授权范围，并能够将复合请求拆解为多个子任务，根据任务需要自主选择允许调用的工具及调用顺序，而不是将所有流程固定写死。程序仍须强制约束可用工具、查询与修改权限、确认机制及模块职责（见
D-001、D-005 至 D-007）。

\*\*示例：\*\*教师要求分析学生甲近期学情、找出薄弱知识点并调整方案，Agent
可调用 B 获取学情与证据、调用 A 查询相关知识关系、调用 C
生成调整方案，再汇总解释。若修改要求不明确，须遵循 D-007
的确认机制后才能实际修改。上述调用顺序仅为示例，并非固定流程。

\*\*设计理由：\*\*允许 Agent
灵活处理复合任务，同时避免越权或绕过各模块的业务规则。证据充分性、任务执行状态、失败处理及回答检查仍待
P-005 讨论。

### D-009：Agent 回答的事实依据

**状态：已确认（总体原则）**

涉及具体学生、课程知识体系、正式学情或学习方案的事实性问题，Agent
必须获取对应模块的实际数据及依据，不得凭空推测。例如，学生薄弱点应依据 B
的学情分析，推荐原因应依据 C 的推荐记录，课程内前置知识关系应依据 A
的知识体系。依据不足时明确说明不足，不强行得出结论。通用知识问题可以由大模型直接回答，但仍须遵守角色权限及其他业务约束。

\*\*设计理由：\*\*保证项目内事实可追溯，同时避免对一般知识问答进行不必要的工具调用。回答中的证据检查与呈现方式仍待
P-005 细化。

### D-010：Agent 任务失败处理

**状态：已确认（总体原则）**

-   暂时性错误允许有限次数的自动重试；具体次数待实现阶段确定。
-   数据缺失时，尝试取得其他有效依据；仍不足则明确说明，不编造结果。
-   关键步骤失败时，停止依赖该步骤的后续操作，不强行生成或修改学习方案。
-   部分任务成功时，保留并展示已完成的有效结果，明确哪些操作失败或尚未完成。

\*\*示例：\*\*B 的学情分析成功但 C 的方案修改失败，Agent
可以展示学情分析，同时明确告知教师方案未修改。

\*\*设计理由：\*\*允许部分完成，但不允许假装完成。重试的具体限制、任务状态记录及防止重复写入的实现细节仍待
P-005、P-011、P-012 细化。

### D-011：Agent 回答中的证据展示与检查

**状态：已确认（总体原则）**

-   学情关键判断须附实际证据；教师可点击引用查看对应原始作答记录。
-   程序检查引用是否存在、是否属于相关学生及授权范围；引用真实不等于结论必然正确，仍需检查结论与依据的一致性。
-   证据不足时明确说明不确定性，不强行下结论。

\*\*设计理由：\*\*让教师能够独立核查分析依据，提升可信度。具体引用结构、界面及检查实现留待
P-005、P-009 细化。

### D-012：Agent 任务范围及学生端调整限制

**状态：已确认（总体任务范围）**

\| 任务类型 \| 教师端 \| 学生端 \| \| \-\-- \| \-\-- \| \-\-- \| \|
学情查询与解释 \| 允许 \| 允许 \| \| 班级学情分析 \| 允许 \| 不允许 \|
\| 课程知识与关系查询 \| 允许 \| 允许 \| \| 学习方案查询与解释 \| 允许
\| 允许 \| \| 学习方案修改 \| 允许 \| 不允许 \| \| 知识讲解与解题引导 \|
允许 \| 允许 \| \| 数据质量查询与解释 \| 允许 \| 不允许 \| \|
学习进展与变化分析 \| 允许 \| 允许 \|

所有任务仍须遵守 D-005 至 D-007 的权限及确认约束。学生端 Agent
不受理学习方案调整请求，不增加通过对话向 B、C
提交调整反馈的入口。学生通过完成 C 推荐的题目产生实际学习反馈，按 D-004
更新方案；额外调整需求可线下向教师提出。

\*\*设计理由：\*\*以实际作答为反馈依据，避免增加重复反馈渠道及 B、C
的处理工作量。任务类型属于原总设计的细化，已有任务路由和部分工具可复用，具体映射与缺失工具待
P-005、P-012 核对。

### D-013：Agent 多轮对话中的对象承接

**状态：已确认（总体规则）**

Agent
可以在多轮对话中继承明确的任务对象和相关信息，无需用户重复指定。切换对象时重新确定操作范围；每次实际修改前均须重新校验对象及权限，对象不明确时向教师确认。不得沿用上一轮的修改授权来操作其他对象。

\*\*设计理由：\*\*兼顾自然对话体验和操作安全。原设计已有上下文管理设想，现有代码支持传入历史对话，仍需完善对象承接及切换校验。

### D-014：学生端双层解题辅助

**状态：已确认（总体设计）**

-   学生在学习计划页面完成 C 推荐的题目时，可按需逐级展开 C
    预先提供的分级提示。
-   已有提示仍不能解决困难时，学生可以向 Agent
    寻求进一步的动态提示；Agent
    在未完成练习时只引导、不直接给出答案，完成后可结合实际作答详细讲解。
-   建议 Agent
    获取当前题目、已有作答及已展开的提示，避免重复提示；建议记录分级提示和额外解题帮助的使用情况，供
    B 区分独立完成与辅助完成。上述两项配套实现细节待 P-007/P-010 确认。

\*\*设计来源：\*\*原总设计已有学习计划页面的分步提示，C
已有提示及防泄答校验基础；本决议明确与 Agent 动态引导的衔接。

### D-015：学习方案自动审核标准

**状态：已确认**

审核推荐依据是否符合实际学情、题目是否匹配知识点、学习顺序是否符合必要前置关系、学习负担是否合理、提示是否有效且不泄露答案、题目是否真实存在且不重复。通过后自动发布，不通过按
D-016 处理。具体判定阈值和实现仍待细化。

### D-016：自动审核失败处理

**状态：已确认**

C
优先自动修正可处理的问题（如题目重复、数量超限、题目匹配不当），修正后重新审核。经过有限次数修正仍不通过，或证据不足、策略不确定性明显等确需人工判断的情况，交由教师审核。具体重试次数与人工处理流程待细化。

### D-017：Agent 记忆与数据库分工

**状态：已确认（总体原则）**

-   当前对话中的任务对象与上下文通过对话历史维持，遵守 D-013
    的对象识别和权限重新校验要求。
-   学情、历史学习方案、作答记录等长期事实由数据库保存，Agent
    通过授权工具按需查询。
-   暂不另建独立长期记忆系统，也不让 Agent 自行维护与 B 并行的学生画像。

\*\*设计理由：\*\*避免重复存储、事实冲突和不必要的开发工作。上下文裁剪及历史数据查询的具体实现仍待
P-005、P-011 细化。

### D-018：Agent 重要操作记录

**状态：记录原则已确认；建议持久化入数据库，具体存储结构待讨论。**

-   记录重要操作，尤其是学习方案修改：教师身份、原始指令、实际修改内容、修改前后方案版本、执行结果和审核结果。
-   普通问答无需同等详细的操作日志。
-   复用已有工具调用记录和方案版本机制；重要操作日志建议持久化至数据库，与方案版本关联，支持追溯、撤销和排错。
-   此前静态审查发现主分支工具调用记录随回答返回，D
    集成分支已有部分推荐修改历史，但完整 Agent
    操作日志持久化尚未实现；未重新核查仓库。
-   具体日志字段、访问权限、保留范围及数据库结构留待 P-011 细化。

### D-019：Agent 任务执行进度展示

**状态：已确认**

前端展示真实、简洁的任务执行进度，例如获取学情、查询知识关系、调整方案、审核结果等。复用已有工具调用记录，实际执行状态与展示保持一致，不展示内部推理、完整提示词及技术参数。具体前端交互与实时状态传输方式留待
P-009、P-010 和 P-012 细化。

### D-020：教师介入提醒与 Agent 分工

**状态：已确认（总体原则）**

B、C
根据学习数据及策略判断是否需要教师介入，教师端自动展示提醒。教师可通过
Agent 查询提醒依据并讨论解决方案。Agent
不需要持续在后台监控学生。具体触发标准、提醒展示和状态管理留待 B、C
及教师端设计讨论。

\*\*设计理由：\*\*复用业务模块的判断能力，减少不必要的模型调用，避免职责重叠。

### D-021：A 模块自动化构建与异常审核

**状态：总体原则已确认**

A
应自动提取知识点及关系、校验原文依据和逻辑合理性、自动修正可处理的异常，仅将无法可靠判断的内容交由人工审核。用户指出可能需要增加前端功能。建议扩展教师端现有「课程体系」页面，设置课程知识体系展示与异常审核两个板块，支持异常候选的修改、通过和拒绝；该页面安排尚待确认。具体算法、判断标准与发布流程仍待讨论。

### D-022：课程体系页面与异常审核

**状态：已确认**

扩展教师端现有"课程体系"页面，设置正式知识体系展示和异常审核两个板块，不另设独立知识库管理页面。正式知识体系展示知识点、课程要求、知识关系及关联材料；异常审核板块仅处理
A 无法自动可靠判断的内容，支持修改、通过和拒绝。正常情况下由 A
自动构建、校验和修正。

**待讨论：** A
的知识提取算法是否采用大模型与规则程序结合，复用教材读取与章节划分程序，引入基于教材原文的模型提取及复核，并保留异常审核兜底。此项尚未确认。

### D-023：A 模块引入大模型

**状态：总体方向已确认，具体分工待讨论**

A
采用大模型与规则程序结合的方式，提高知识点提取、知识关系判断和校验能力，减少人工审核依赖。具体调用流程、模型与程序的职责划分、原文依据校验及异常处理仍待
P-004 讨论。

### D-024：A 中大模型与规则程序的总体分工

**状态：已确认（总体流程）**

### 10.3 B 与大模型协作的强制设计要求

1.  程序负责原始数据清洗、修订选择、状态识别、得分/满分、分母、班级汇总、证据门槛、掌握分级、版本与权限。
2.  大模型负责需要数学语义理解的学生步骤解析、评分点对齐、错误根因候选、在线解答题评分候选、师生文字诊断和班级文字摘要。
3.  模型不得直接写数据库、改变官方得分、创建正式知识点/题目/评分点、跳过
    A 版本或证据校验。
4.  生成与复核分开调用；模型意见冲突先仲裁，仍不确定才交教师。
5.  所有模型输出必须是严格结构化结果，引用真实作答片段和
    EvidenceRef，并由程序验证 ID、原文、分值、总分、版本和权限。
6.  模型故障时保留确定性分析；无法可靠评分的在线解答题保留作答并标待评分/待审核。
7.  文字诊断只能从已验证结构化结果生成；数字、知识点名称、错误类型、进展结论不得由模型自由增补。
