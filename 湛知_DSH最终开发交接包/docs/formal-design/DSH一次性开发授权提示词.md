我一次性授权你在 GitHub 仓库 rwissez/smart-study-companion 的独立开发分支内，按本交接包完成湛知全量开发、整合、测试、修复和交付。现在从 P0 开始执行，请实际修改代码并运行测试。通过一个阶段后自动开始已满足依赖的下一个阶段，无需逐阶段等待我确认。

1. 开始时实际读取交接包根目录 AGENTS.md、docs/formal-design 下的 00—09、07 视觉规范、决策 v0.55-draft、最终一致性检查报告和最终待确认问题清单。使用本包内的最新版；v0.54 用于历史对照。核对远端 main、D 集成分支、相关 A/B/C 分支、实际锁文件、联调代码、工具能力及现有改动。原审阅分支是 Codex 本地文档来源，若远端找不到，直接使用我提供的已核验 ZIP。
2. 按 08 从核定后的 main 创建独立最终开发分支，保护原始工作区。逐文件复用和选择性整合 D 与其他分支，保留 main 有效能力；把本包 AGENTS.md 放到实际代码仓库根，规范及资产保留 docs/formal-design 路径。你负责本地开发分支、提交、冲突处理、整合和已授权远端上的开发分支推送。受保护分支或 main 的最终合并遵守仓库授权、审批及 09 正式验收，不直接改 main 或强推。
3. 先串行完成共享接口、数据库迁移、权限及任务基础并冻结合同。具备并行和工作区隔离能力时，按 08 的四条工作线开发；不足则自动串行。C 正式接入等 A/B 验收，Agent 等 C 服务，前端真实接入等相应 API。只有遇到无法自行解决的设计冲突、权限限制或必需外部依赖时，才暂停受影响任务并继续其他授权工作。优先使用文件中明确的服务与权限语义，不替我重开已确认的业务设计。
4. 完整交付 A/B/C、Agent、教师和学生双端、统一 SQLite 迁移、后台任务、权限、版本和正式 ZIP 导出。按 07 原图和视觉规范完成界面。落实三个计划发布路径、实际学习事件与帮助手续，以及合规最终失败任务一次手动重试。使用已确认的 API 与状态，保护历史、原始数据和答案，模型不可用按方案降级，正式模式不回退演示数据。
5. 每阶段按 09 执行测试，失败先定位、修复再复测；通过后记录提交与证据再向后推进。维护 execution_state.json 和 DEVELOPMENT_PROGRESS.md。按阶段给出简明进度，包括已实现内容、实际通过/失败/未执行的测试、受影响范围、下一步及我必须解决的具体阻塞。静态检查、合成测试、真实接口联调、真实模型、授权赛方数据与人工截图验收分别记录；任何未执行的项目不得写成通过。
6. 最终从干净环境安装、迁移、启动，并用真实 API 完成上传→正式 A/B/C→教师或 Agent 合规修改→学生微课堂/作答→B 学情更新→C 复查→正式导出。按 09 验证合规真实模型、重启恢复、三学生两班案例、视觉与数据隔离。交付候选分支与 commit、启动说明、锁及迁移、正式包、实测命令和结果、截图、未解决问题。核心缺失、S0/S1、不可重现或未完成必要真实验收时，明确报告尚未通过。

请立即开始 P0。首次进展报告附 Git/环境及资料核对结果，然后继续工作，除非遇到上述真实阻塞。
